## 一、分层与依赖规则

DDD 四层，依赖方向严格单向：

```
interfaces       用户接口层   Controller、DTO、错误状态映射
                              ← 兼作防腐层（ACL）：JSON ↔ 领域对象，两侧不互相渗透
application      应用层       用例编排、策略注入 —— 不含业务规则
domain           领域层       全部业务规则
infrastructure   基础设施层   Spring 装配、配置绑定

依赖方向：interfaces → application → domain ← infrastructure
```

### 1.1 铁律：`domain` 不认识框架

**`domain` 包不 import 任何 `org.springframework.*`。**

本期实测：`grep -rn "org.springframework" src/main/java/com/wysjwxm/calculator/domain/` → **0 命中**；
`domain` 反向 import `application` / `interfaces` / `infrastructure` 也是 **0 命中**；
`application` 反向 import `interfaces` / `infrastructure` 同样是 **0 命中**。

**为什么写成铁律，而不是「尽量遵守」：**

1. **它让领域层可被最纯粹地单测。** 领域测试不需要 Spring 上下文，跑得快、失败时定位准。
2. **它让业务规则不依赖框架的版本与生命周期。** 领域对象是纯粹的 Java 类型，框架换版本、换容器都不影响它们。
3. **它是可机械验证的。** 一条 `grep` 就能查出破口，不依赖评审者的记性 —— 规则若不可验证，就只是愿望。

正因为这条规则可验证，它才值得写成铁律。

### 1.2 配置类不穿过分层边界

`CalculatorProperties` 是 Spring 绑定类，属基础设施关切，因此留在 `infrastructure/config`；
由同包的 `CalculatorConfiguration` 把它**翻译**成下游可用的 bean。本期实际装配的 7 个 bean：

| bean | 类型 | 谁消费 |
|---|---|---|
| `Numbers` | 领域服务 | `ExpressionEvaluator` |
| `FunctionRegistry` | 领域对象 | `ExpressionEvaluator` |
| `ExpressionParser` | 领域服务 | `CalculationUseCase` |
| `ExpressionEvaluator` | 领域服务 | `CalculationUseCase` |
| `CalculationPolicy` | **应用层的纯 Java record，无框架残留** | `CalculationUseCase`、`CapabilityQuery` |
| `CalculationUseCase` | 应用服务 | `CalculatorController` |
| `CapabilityQuery` | 应用服务 | `CapabilityController` |

计数口径说清楚：`CalculatorConfiguration.java` 里是 **7 个 `@Bean` 方法**，
其中前 6 个构成求值路径，第 7 个是能力清单用例 —— 这与 `CalculatorConfigurationTest`
的 `registersExactlyTheSixEvaluationPathBeans`（`CalculatorConfigurationTest.java:51`）的「6」并不矛盾：
那条测试数的是**求值路径**上的 6 个。
另注意 `ReservedNames` **不是** bean（它由 `ReservedNames.standard()` 静态求得）；
`CalculationCommand` 是接口层 `new` 出来的，不参与装配。

关键点是 `CalculationPolicy`：`application` 只依赖这个**无注解的 record**，不 import `CalculatorProperties`。
配置类因此不能从基础设施「漏」进应用层，依赖方向不被破口。

## 二、限界上下文与统一语言

**限界上下文只有一个：表达式计算上下文。**

变量、求值、能力清单三者共用同一套词汇 ——「变量名」在这三处含义完全相同，
不存在需要翻译的同形异义词，也没有需要隔开的团队边界。硬拆成多个上下文只会引入
**没有翻译内容的防腐层**。**判断「不拆」与判断「拆」同样是 DDD 的设计动作**，此处如实记录结论。

统一语言：代码类名与文档用语一一对应，不使用同义词、不做别名。

| 领域概念 | 类型 | 代码元素 | 本期 |
|---|---|---|---|
| 表达式原文 | 值对象 | `ExpressionText`（构造即校验：非空白） | 有 |
| 表达式 | 值对象 | `Expression`（sealed AST 及节点） | 有 |
| 数值 | 值对象 | `CalcNumber` / `DecimalNumber` / `FloatingNumber` | 有 |
| 算符 | 值对象 | `Operator`、`OperatorTable` | 有 |
| 函数 | 值对象 | `MathFunction`、`UnaryFunction`、`BinaryFunction` | 有 |
| 保留常量 | 值对象 | `MathematicalConstant` | 有 |
| 保留名集合 | 值对象 | `ReservedNames`（函数名 ∪ 常量名） | 有 |
| 角度制 | 值对象 | `AngleUnit` | 有 |
| 变量名 | 值对象 | `VariableName`（构造即校验，无旁路） | **顺延** |
| 变量 | 实体 | `Variable`（身份 = `VariableName`） | **顺延** |
| 变量表 | 聚合根 | `VariableSet` | **顺延** |
| 计算 | 实体 | `Calculation`（身份 = id） | **顺延** |
| 计算历史 | 聚合根 | `CalculationHistory` | **顺延** |

「本期」列如实标注了顺延项 —— 统一语言表是**目标状态的词汇表**，
但不应让人误以为表里的类都已存在。

## 三、数值模型

### 3.1 两条路径写进类型里

```java
sealed interface CalcNumber permits DecimalNumber, FloatingNumber {
    double toDouble();
    BigDecimal toDecimal();
}

record DecimalNumber(BigDecimal value) implements CalcNumber { }
record FloatingNumber(double value)    implements CalcNumber { }
```

**设计意图**：`0.1 + 0.2` 必须精确等于 `0.3`（计算器的基本可信度），
而 `sin` / `log` / `exp` 在实现层面只能是浮点。用一个 `sealed` 类型把两条路径显式分开，
让「哪里精确、哪里不精确」成为**类型系统里可读的事实**，而不是散落在各处的隐式约定。

`permits` 是穷尽的：新增第三种数值形态必须显式改动这个声明，不可能悄悄混进来。
求值器与提升逻辑对这两条路径的处理因此可以被编译器与测试同时钉住。

### 3.2 类型提升规则（集中在 `Numbers`，不在求值器里散落）

| 场景 | 规则 |
|---|---|
| `+ - *` 双方均 `DecimalNumber` | 走 `BigDecimal` 原生运算，结果**精确** |
| `/` | 能整除时**精确**（先试 `dividend.divide(divisor)`）；除不尽按配置精度截断，默认 `MathContext(34, HALF_EVEN)`，故 `1/3 → 0.3333333333333333333333333333333333` |
| `%`（取余） | 双方 `Decimal` 时走 `BigDecimal.remainder`；否则降级 `double` |
| 任一侧为 `FloatingNumber` | 整体提升为 `FloatingNumber`，走 `double` |
| 超越函数返回值 | 一律 `FloatingNumber` |
| `^` | 指数为非负整数且底数为 `Decimal` 时，走 `BigDecimal.pow` 保持精确；否则走 `Math.pow` |
| 结果规整 | `double` 结果按 **15 位有效数字**规整（`MathContext(15)`，`HALF_EVEN`），消除 `sin(30) = 0.49999999999999994` 一类毛刺 |

**保底不变量**：任何运算结果只要落到 `DecimalNumber`，就永远精确；
一旦沾了 `FloatingNumber`，即存在浮点误差。这条不变量在测试中固定。

规整的代价要说清楚：绝大多数结果的末 1~2 位被改写，相对误差上限约 `5e-15`。
这是**为消除毛刺付出的代价**，不是意外。

### 3.3 数值范围是公开契约

支持范围的上界（scale 上界、精确幂位数预算、阶乘上界、除法精度、表达式长度、
反双曲自变量上界、`round` 上界）**逐条写进了 README 的「数值计算范围」一节**，
每个数字都带 `文件:行号`。

架构上值得记的是**边界的处理策略**：范围之内保证算得对；范围之外**一律拒收**
（抛 `CalcException` 走 4xx），不保证给出哪个错误码，也**不承诺优雅降级**。
刻意不追求「对任意极端输入都给出有意义结果」——那种目标没有上界，
而计算器的价值在于对**常用域**精确可靠。

由此得出一条实现纪律：**超出范围的输入只需抛异常，实现者不得为此扩增边界处理代码**。
这条纪律挡住了「为极端输入写特例」这一类持续膨胀的复杂度。

另外两条与数值相关的实现细节值得一提：

- **浮点规整不作用于内置常量。** `pi` / `e` 直接构造 `FloatingNumber`
  （`MathematicalConstant.java:45-47`），绕过规整 —— 它们是常量的**精确 double 表示**，
  不是计算结果，不该被「消除毛刺」的逻辑改写。
- **字面量走精确路径。** 表达式里写进来的数经 `new DecimalNumber(new BigDecimal(lexeme))`
  直接构造（`parse/ExpressionParser.java:151-161`），因此 `0.1` 是**精确的 0.1**，
  不是 double 的近似值 —— 这是 U2「`0.1+0.2 = 0.3`」成立的另一半原因。

## 四、表达式语言规范

### 4.1 词法

| Token | 形态 |
|---|---|
| `NUMBER` | `123`、`1.5`、`.5`、`1e-3`、`1.5E+10` |
| `IDENT` | `[A-Za-z_][A-Za-z0-9_]*`，用于函数名、变量名、保留常量名 |
| `PLUS` `MINUS` `STAR` `SLASH` `PERCENT` | `+ - * / %` |
| `CARET` | `^` |
| `BANG` | `!`（阶乘） |
| `LPAREN` `RPAREN` | `( )` |
| `COMMA` | `,`（多参函数） |
| `EOF` | 流结束 |

每个 Token 携带 `position`（起始字符下标，0 基），供错误定位使用 ——
这是错误响应里 `position` 字段的来源。

### 4.2 语法

语言规范（递归下降形式）：

```
expression → term (('+' | '-') term)*
term       → unary (('*' | '/' | '%') unary)*
unary      → ('+' | '-') unary | power
power      → postfix ('^' unary)?            // 右结合
postfix    → primary ('!')*
primary    → NUMBER
           | IDENT '(' args? ')'             // 函数调用
           | IDENT                           // 变量或保留常量
           | '(' expression ')'
args       → expression (',' expression)*
```

**实现策略与规范不同，这是刻意的**：实现采用**优先级爬升（precedence climbing）**的递归下降解析器，
由 `OperatorTable` 驱动，而不是把优先级硬编码成嵌套方法。

原因值得记下来：硬编码会在语法里写一遍优先级、在 `/functions` 清单里再写一遍，
**两处必然漂移**。更糟的是防漂移测试会通过（清单与算子表一致），
而算子表与解析器**实际行为**不一致 —— 测试形同虚设。
由算子表统一驱动后，`precedence` / `associativity` **只有一处定义**，
清单与解析器读的是同一份数据。

### 4.3 优先级与结合性：`OperatorTable` 是唯一事实来源

`OperatorTable` 里 9 个算子的完整定义（`OperatorTable.java:24-33`）：

| 符号 | 定位 | 优先级 | 结合性 | 语义 |
|---|---|---|---|---|
| `+` | `INFIX` | 1 | 左 | 加 |
| `-` | `INFIX` | 1 | 左 | 减 |
| `*` | `INFIX` | 2 | 左 | 乘 |
| `/` | `INFIX` | 2 | 左 | 除 |
| `%` | `INFIX` | 2 | 左 | 取余 |
| `-`（一元） | `PREFIX` | 3 | 无 | 取负 |
| `+`（一元） | `PREFIX` | 3 | 无 | 取正 |
| `^` | `INFIX` | 4 | **右** | 幂 |
| `!` | `POSTFIX` | 5 | 无 | 阶乘 |

（同一符号 `+` / `-` 在前缀与中缀位置各有一个定义，因此表里是 9 个条目、6 种拼写。）

由此得出的三条可观测结论（均以测试固定，spec §6.3）：

- `^` **右结合**：`2^3^2` = `2^9` = `512`
- 一元正负号优先级**低于** `^`：`-2^2` = `-4`（不是 `4`）
- `!` 阶乘**高于**所有二元算子：`3! + 1` = `7`

**一句必须写进契约的话**：`/functions` 把优先级与结合性**暴露成了对外契约**。
调整 `OperatorTable` 里的优先级会改变该接口的响应。这是有意的 ——
该接口的定位就是**如实描述表达式语法**。`OperatorTableTest` 保证清单与实现不漂移。

### 4.4 命名空间：保留常量与用户变量

- **保留常量**（只读，不可被用户变量覆盖）：`pi`、`e`。
- **用户变量名的禁用集合 = 函数名 ∪ 保留常量名**（本期 23 + 5 + 2 = 30 个）。

之所以把常量也列入保留名：若允许 `pi = 3`，`sin(pi)` 的含义会随调用方的写入操作**静默改变**，
表达式的可重现性被破坏。常量是语言的一部分，不是可被覆盖的缺省值。

求值期 `IDENT` 的解析规则是**常量优先**：先查保留常量，未命中则查用户变量，
仍未命中抛 `UNKNOWN_VARIABLE`。求值器**刻意不依赖**入口校验来保证这一点 ——
领域层自己定义语义，入口拒收是另一道把关。

**目标设计里这条规则由类型系统落实**：禁用集合是值对象 `ReservedNames`，
用户变量名必须构造为 `VariableName` 才能进入任何 API，而 `VariableName` 的构造器**本身就拒绝保留名**
——「不合格的名字根本造不出对象」，不变量由类型系统保证而非调用者的自觉保证。

**本期现状（如实说明）**：MVP 未引入 `VariableName`，该项校验暂落在应用层的
`CalculationCommand` 紧凑构造器内（`application/CalculationCommand.java:29-48`），
对请求级 `variables` 的键与值做校验，命中保留名或 null 即抛 `INVALID_REQUEST`。
spec §6.4 末尾对此有明确交代：Phase 2 引入变量存储时按 D13 收口到值对象，
届时那段才转为对现状的描述。

## 五、HTTP 契约

统一前缀 `/api/v1`。请求与响应均为 `application/json; charset=UTF-8`。
本期交付 **3 个端点**：

| # | 方法 | 路径 | 说明 |
|---|---|---|---|
| 1 | `POST` | `/api/v1/calculator/calculate` | 表达式求值 |
| 2 | `GET` | `/health` | 健康检查（**不带前缀**，spec 端点表与 §7.5 两处均明文如此） |
| 3 | `GET` | `/api/v1/calculator/functions` | 能力清单 |

### 5.1 求值请求与响应

请求字段：`expression`（必填、非空、长度 ≤ `calculator.max-expression-length`）、
`angleUnit`（可选，缺省取配置）、`variables`（可选，**请求级临时变量**，仅本次求值生效）。

响应字段：`expression`、`result`、`resultType ∈ {DECIMAL, FLOATING}`（标明结果落在哪条数值路径上）、
`angleUnit`。

两点契约细节值得单独指出：

- **`angleUnit` 仅在表达式真的用到角度敏感函数时才回填。** 实现上由
  `AstInspection.usesAngleSensitiveFunction` 判定（`application/CalculationUseCase.java:52-56`），
  AST 里没有相关函数时该字段为 `null`。因此 `1+2` 的响应里 `angleUnit` 在场且为 JSON `null`
  ——「本次求值不涉及角度」这一事实被如实表达，而不是靠字段缺席。
- **`/functions` 的清单由源码生成，不另写一张表。** 常量、一元函数、二元函数分别来自
  `MathematicalConstant.values()`、`UnaryFunction.values()`、`BinaryFunction.values()`，
  算子直接取 `OperatorTable.all()`，上限来自 `CalculationPolicy` 与
  `Numbers.MAX_EXACT_DIGITS` / `DecimalNumber.MAX_SCALE_MAGNITUDE`（`application/CapabilityQuery.java:37-48`）。
  **唯一由人填写的是 `endpoints`**（`interfaces/CapabilityController.java:33-36`）——
  路由是接口层才知道的事实，应用层不认识 HTTP 路径。
  清单顺序即契约：保持枚举声明顺序，**不排序、不去重**。

`endpoints` 这份手写数据有专门的守卫：`CapabilityEndToEndTest` 在**真实 HTTP 栈**上
把清单里的端点与 `RequestMappingHandlerMapping` 里注册的路由对账，
多报漏报都会失败。**手写的部分被测试锁住，生成的部分由结构保证** —— 两者合起来才等于「清单不会漂移」。

## 六、错误处理

### 6.1 错误码词汇表（12 个）

`domain/error/CalcErrorCode.java:10-21` 的 12 个常量，与 HTTP 状态的映射如下
（映射集中在一处：`interfaces/error/ErrorStatusMapper.java:20-29`）：

| HTTP | code | 触发条件 |
|---|---|---|
| 400 | `PARSE_ERROR` | 语法错误，响应含 `position` |
| 400 | `INVALID_REQUEST` | 字段缺失 / 类型不符 / 越界 / 格式非法 / 变量名落入禁用集合 |
| 400 | `UNKNOWN_FUNCTION` | 调用了未注册的函数名 |
| 404 | `VARIABLE_NOT_FOUND` | 查询或删除不存在的变量（**本期无此端点**） |
| 404 | `HISTORY_NOT_FOUND` | 查询不存在的历史记录（**本期无此端点**） |
| 404 | `NO_HANDLER` | 路径不存在 |
| 405 | `METHOD_NOT_ALLOWED` | 方法不匹配 |
| 422 | `UNKNOWN_VARIABLE` | 表达式引用了未定义变量 |
| 422 | `DIVISION_BY_ZERO` | 除零、模零 |
| 422 | `DOMAIN_ERROR` | 违反函数定义域 |
| 422 | `NON_FINITE_RESULT` | 结果溢出为 Inf/NaN、阶乘超界 |
| 500 | `INTERNAL_ERROR` | 兜底，不外泄堆栈信息 |

> `UNKNOWN_OPERATOR`（v1 有）已随结构化算子接口一并删除。
> 错误码词汇表**保持完整是刻意的**（见 [`docs/mvp-and-roadmap.md`](mvp-and-roadmap.md) §五）：
> 词汇表是**领域的字典**，不因本期没有对应端点就删词。

统一响应体（spec §7.6）：`code`、`message`、`position`、`timestamp`、`path`。
`position` 仅在**与位置相关**的错误中出现，其余为 `null`。

### 6.2 防漂移机制（两道网，各管一段）

**第一道网是编译期的。** `ErrorStatusMapper.toStatus` 是一个**没有 `default` 的穷尽 `switch` 表达式**：
新增一个 `CalcErrorCode` 却忘了给它状态，代码**直接编译失败**，跑不到测试阶段。
这是本设计里最强的防漂移手段 —— 它不依赖任何人记得跑测试。

**第二道网是测试，但它的目标与「第一道网」不同。**
`ErrorStatusMapperTest` 做两件事：

1. 遍历 `CalcErrorCode.values()` 断言每个码都有映射 —— 在当前的穷尽 `switch` 下
   **这条断言不可能失败**，它守的是「有人给 `switch` 加了 `default`」这类回退。
2. **钉住每个码具体映到哪个状态**（例如「`INTERNAL_ERROR` 是唯一映到 500 的码」）
   —— 这才是真正带防变异能力的那一条。

**把这道网说清楚很重要**，因为 spec 里有一处表述需要更正：spec §7.6 末尾与 §10 关键测试点
两处**把防漂移的第一道网说成了测试**（「由 `ErrorStatusMapperTest` 断言……」）。
按本期实现，**第一道网是编译期**，`ErrorStatusMapperTest` 覆盖的是编译器覆盖不到的那半
——「哪个码映到哪个状态」。权威表述见
`src/test/java/.../ErrorStatusMapperTest.java` 的类注释（本项目对这两道网最准确的措辞）。
（spec 里那两处说的是 `:527` 与 `:602`。）

### 6.3 错误处理分支的覆盖缺口（如实记录）

`GlobalExceptionHandler` 有 **6 个** `@ExceptionHandler` 分支
（`interfaces/error/GlobalExceptionHandler.java` 的 `:33`、`:38`、`:45`、`:53`、`:66`、`:78`），
其中 **5 个被测试真实触达**，**1 个本期不可达**：

| 分支 | 位置 | 本期状态 |
|---|---|---|
| `CalcException` | `:33` | 触达（各错误码用例） |
| `NoHandlerFoundException` | `:38` | 触达（E14 未知路径） |
| `HttpRequestMethodNotSupportedException` | `:45` | 触达（E13 方法不符） |
| `HttpMessageNotReadableException` | `:53` | 触达（E4 非法 JSON） |
| `MethodArgumentTypeMismatchException` | `:66` | **不可达** |
| `Exception`（兜底） | `:78` | 触达（E15 非 JSON 请求体） |

**唯一不可达的分支是 `MethodArgumentTypeMismatchException`**，原因是本期 3 个端点
都不绑定路径变量或查询参数，没有「参数类型不符」这个可能。它映射到
`INVALID_REQUEST`，是 spec §7.6 错误码表里「类型不符」那一行的实现。

**为什么保留而不删除**：它与被删掉的 `policy` 字段性质不同。

- 被删的 `policy` 字段是**死重** —— 单入口下它恒为同一个值，删掉它不损失任何表达能力。
- 这个分支是**当前不可达、但语义完整**的实现 —— 它是词汇表里一个码的落地实现，
  Phase 2 加入带路径变量的端点后立即生效。删掉它就得同时删掉错误码，
  而**错误码词汇表保持完整是刻意的**（roadmap §五）：词汇表是领域的字典，
  不该随着「本期有没有这个端点」伸缩。

换句话说：**删字段是去掉冗余，删分支是砍掉词汇表的一部分**，两者不能类比。

**兜底分支的说法要准确**：它不是死分支，而是
**在出厂配置下即可由客户端错误到达的兜底分支** —— 出厂配置下，
`Content-Type` 非 JSON 的请求会先抛出 `HttpMediaTypeNotSupportedException`，
本类没有该分支，于是落到兜底返回 500 `INTERNAL_ERROR`（用例 E15 实测）。
（另：把接口层的参数守卫去掉这类缺陷，也会从求值路径落到这里。）

**已知边界，不是缺陷，也不为它造断言**：传 `Accept: application/xml` 时实测得到
**406 + 空响应体** —— 兜底 handler 被调用了一次，但它产出的 JSON 在「客户端只接受 XML」
的前提下渲染不出来。spec 未定义 406 的语义，因此这里**如实记为边界**，
而不是编一条断言把它「固定」成一个没人论证过的契约。

## 七、设计决策记录（含被否决的方案）

保留**否定方案**的理由比只留结论更有价值 —— 它说明边界是被论证出来的，不是随手划的。
D1–D9 出自 v1→v2 评审（收敛功能边界）；D10–D13 出自 v2→v3 评审（改换架构风格）。
以下 13 条中，**D11–D13 是本期最有现实意义的三条**（它们决定了本期代码的形态）。

| # | 决策 | 结论 | 理由 |
|---|---|---|---|
| **D1** | v1 设计了 `POST /binary`、`POST /unary` 结构化算子接口 | **砍掉** | 功能被 `/calculate` 完全覆盖：`{operator:"add",left:1,right:2}` 与 `{expression:"1+2"}` 语义等价。唯一站得住的理由是「客户端不必拼字符串」，但能力清单暴露算子符号后，客户端照清单拼即可，该理由不成立。**连带简化**：历史记录的 `type` 字段失去意义，一并删除 |
| **D2** | v1 设计了内存寄存器（`M+`/`M-`/`MR`/`MC`） | **砍掉** | HTTP 客户端可自行持有状态，且变量可完全替代。唯一不可替代点是 `M+` 的原子读-改-写，但单用户场景下无意义 |
| **D3** | v1 同时提供 `pow`/`mod` 函数与 `^`/`%` 运算符 | **删掉 `pow`/`mod`** | 同一能力两种拼写，是设计噪音。`^`/`%` 是中缀数学写法，更符合计算器心智。**一般化的规则**：函数集只收录无法用中缀表达的运算 |
| **D4** | v1 允许用户变量覆盖内置常量（`pi = 3`） | **改为保留名** | 覆盖会让 `sin(pi)` 的含义随写入操作静默改变，破坏表达式可重现性。常量属于语言，不属于缺省值。**连带简化**：变量名禁用集合统一为「函数名 ∪ 常量名」，且在**存储写入与请求级临时变量两个入口统一生效**，不为「临时、不落库」开口子 |
| **D5** | v1 用 `type` 字段区分历史记录来源 | **删除** | D1 的连带结果，单入口下该字段恒为同一值，是死重 |
| **D6** | 历史淘汰：FIFO 还是 LRU | **FIFO** | 只追加的数据无访问频次语义。**属 Phase 2 设计**（本期无历史存储） |
| **D7** | `/health` 是否保留 | **保留** | 价值低（仅冒烟测试与探针惯例）但成本近零（5 行），且直接服务验收标准第 2 条 |
| **D8** | `/functions` 的定位 | **能力清单** | v1 把它写成并列的两个列表，导致 `^` 与 `pow` 看起来像两种能力。改为如实描述表达式语法（算子含 `fixity`/`precedence`/`associativity`），并**由 `OperatorTable` 直接生成**，杜绝清单与实现漂移 |
| **D9** | Spring Boot 版本 | **4.1.1 → 3.5.x** | 原脚手架为 4.1.1，题目文字约束为「SpringBoot3」，以题目为准 |
| **D10** | v2 的分层是 `core / api / service / store / config` | **改为 DDD 四层** `domain / application / infrastructure / interfaces` | 原分层是**技术分层**：`core` 是「纯计算」、`store` 是「存储」、`service` 是「服务」—— 按代码的技术角色划分。DDD 四层按**依赖方向与职责边界**划分，`domain` 承载全部业务规则、`application` 只做编排。真正的收益在 D11–D13，其余是改名 |
| **D11** | 聚合根与仓储是否分成两个类型 | **合并** —— 领域层声明聚合根接口，基础设施层提供内存实现 | 教科书式分离的前提是**存在持久化**：加载要查库、保存要写库，是真实的、可能失败的操作，值得单独抽象并承载事务语义。本系统纯内存，聚合根本身就是存储，再加一层仓储只是把调用原样转发一遍。**为不存在的复杂度预留抽象不是设计，是负债** |
| **D12** | 是否引入领域事件（如 `CalculationPerformed`）+ 事件发布器 | **不引入** | 领域事件的价值在于**跨聚合、跨上下文的最终一致性**。本设计只有一个限界上下文、只有一个聚合需要在计算后被写入，且该写入是同步的、属于同一个用例 —— 用事件解耦等于把一个方法调用拆成「发布 + 监听」两跳，只增加间接层。**在文档里说明为什么不引入，比引入了更值钱**；同理不做规约模式、工厂类、CQRS |
| **D13** | 变量名的保留名校验放在哪 | **全部放进值对象的规范构造器**，不引入领域服务 | 曾被否决的中间方案：既然保留名依赖函数表，而值对象构造器「拿不到外部上下文」，那就加一个领域服务 `VariableNames` 来产出变量名。**此方案被推翻** —— 函数集与常量集都是编译期固定的枚举，保留名集合静态可求，压根不是「运行时上下文」。既然构造器能独立完成格式、长度、保留名三项校验，那层领域服务就是多余的间接层。校验在类型里，没有旁路 |

**关于 D11–D13 的现实意义**：本期没有变量存储，因此 D11 / D13 的直接产物
（聚合根接口、`VariableName` 值对象）尚未落地，但它们的**精神已经生效** ——
D12 的「不引入」直接决定了本期没有事件发布器这一层；
D13 的「校验放进类型 / 尽量靠近类型」体现在 `CalculationCommand` 的紧凑构造器上。

## 八、刻意不引入的东西

这一节与第七节的「被否决方案」互补：第七节记的是**过程中试过又推翻的**，
本节记的是**从未引入、且明确决定不引入的**。

| 不引入 | 理由 |
|---|---|
| 领域事件 + 事件发布器 | 见 D12：跨聚合的最终一致性才有价值；本设计只有一个上下文、一次同步写入 |
| 规约（Specification）模式 | 本设计没有复杂的、需要组合的查询条件 —— 唯一的「查询」是求值与查清单 |
| 工厂类（`*Factory`） | 对象的构造逻辑都不复杂，且**校验已在值对象构造器里**（构造即校验）。再加工厂只是把 `new` 包一层 |
| CQRS（读写模型分离） | 读侧只有能力清单，写侧只有求值，两者没有各自的复杂度压力。分离会引入两套模型与同步问题 |
| 仓储与聚合根分离 | 见 D11：纯内存下聚合根就是存储 |
| 防腐层（ACL）之外的映射框架 | 层间转换手写即可，DTO 与领域对象一一对应，引入映射器/反射框架是**第三方依赖**，与项目约束冲突 |

**这条纪律的表述**：**为不存在的复杂度预留抽象不是设计，是负债。**
每一层抽象都要回答「它挡住了哪个已经存在的复杂度」，答不上来就不加。

## 九、并发与存储（本期现实）

**本期没有任何可变的共享状态，因此不存在并发问题。**

这一句不是「我们没考虑并发」，而是**如实描述当前的架构形态**：

- `domain` 的领域服务全部**无可变实例状态**。尤其 `ExpressionParser` 是刻意设计的
  **无状态**单例：解析游标封在每次 `parse()` 调用创建的局部对象里。
  （spec §4.3 明确记录过这一点在早期草稿中曾写错 —— 把游标做成实例字段，
  那样的实例不可被并发复用。此处重申以防回退。）
- `application` 的 `CalculationUseCase` / `CapabilityQuery` 只持有**不可变的依赖引用**。
- `infrastructure` 的 `CalculatorProperties` 是不可变 record；`CalculatorConfiguration`
  产出的 bean 全是无状态单例。
- **本期没有存储。** 没有变量存储、没有历史存储 —— 意味着没有需要保护的内存结构，
  也就没有锁、没有淘汰策略、没有可见性问题。

因此**本文档不展开任何并发策略**：spec §8 的并发表（不同聚合根各自的数据结构与锁策略、
历史淘汰策略的论证）描述的是**含变量与历史的 Phase 2 设计**，本期没有对应的实现，
照抄过来会让文档描述一个不存在的系统。Phase 2 落地时应回到 spec §8 取值。

**一处需要如实指出的配置现状**：`application.yaml` 里有 `calculator.history-capacity: 1000`，
`CalculatorProperties` 也绑定了它并提供 `historyUnbounded()` 判断 —— **但本期没有任何消费者**
（历史存储本身顺延了）。这个键是为 Phase 2 预留的、当前**空转**的配置。
它保留了，是因为配置项与类一起构成 Phase 2 的接口约定；
但对本期而言必须说清楚：**改它不会产生任何可观测的行为差异**。

## 十、已知取舍（架构层面）

| 项 | 说明 |
|---|---|
| 除法的精度上限 | `1/3` 在 `MathContext(34)` 下为 34 位有效数字，非无限精度。这是刻意的工程取舍 |
| 浮点结果 15 位规整 | 代价是末 1~2 位被改写，相对误差上限约 `5e-15`；换来的是消除 `sin(30)` 一类的尾数毛刺 |
| 反双曲函数的自变量上界 | 手写恒等式里的 `x²` 中间量会先溢出，故收窄到 `√Double.MAX_VALUE`。**声明的范围就是保证正确的范围** |
| `/functions` 暴露优先级 | 优先级数值成为对外契约的一部分，调整解析器优先级会改变响应。**这是有意的** —— 该接口的定位就是如实描述语法 |
| 单实例限制 | 内存存储意味着不支持多实例横向扩展与重启保留。这是题目约束的直接结果，非缺陷 |
| 无鉴权 | 题目未要求；加了需要用户体系，超出范围 |
| `history-capacity` 当前空转 | 见第九节：配置项已绑定但本期无消费者 |
| Spring Boot 降级 | 见 D9 |
