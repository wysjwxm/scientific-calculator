## 一、原始需求

题目给的是一句话的需求，spec §1 原文如此记录：

> 实现一套科学计算器 HTTP 后端服务，仅内存存储，无数据库、无缓存中间件、无任何第三方外部接口调用，打包为可独立运行的 runnable jar。功能边界需自行拆解。

（spec `:13`。同段还有一句定性：这是一份「极简原始需求」。）

这句话里有**三条硬约束**与**一个空白**：

| 类别 | 内容 | 来源 |
|---|---|---|
| 硬约束 | 仅内存存储；无数据库、无缓存中间件、无任何第三方外部接口调用 | 题面 |
| 硬约束 | 打包为可独立运行的 runnable jar（`java -jar` 直接跑） | 题面 |
| 硬约束 | Java 17 + Spring Boot 3 + Maven + JUnit 5（题面另附的技术栈） | 题面 / spec §2 |
| **空白** | **「科学计算器」到底包含哪些能力、哪些接口，题面没有给** —— 这句原话把它显式交给了设计者：「功能边界需自行拆解」 | 题面 |

因此本项目的需求分析不是「把题面抄成列表」，而是**在一次空白上划出边界并论证它**。
后面每一节都在回答同一个问题：**为什么这条线划在这里，而不是更宽或更窄。**

另有一条来自用户的补充要求，直接决定了交付文档的形态：**先明确数值的计算范围**。
它落成了 spec §5.3「数值计算范围（契约）」这一节，以及 README 的「数值计算范围」一节 ——
边界不再是一句「尽量支持」，而是一张写着具体数字的表。

## 二、需求拆解过程

拆解是**三轮收敛**，每一轮都把上一轮的边界收窄一次。这条路径本身是需求分析的主要产出。

### 第 1 轮：从「科学计算器」铺开能力全集（v1）

按「一个计算器应用通常有什么」铺开，得到：结构化算子接口（`POST /binary`、`POST /unary`）、
内存寄存器（`M+` / `M-` / `MR` / `MC`）、变量寄存器、计算历史、能力元数据、健康检查，
外加用户体系、鉴权、多租户、持久化、表达式化简与符号求导、方程求解、复数、矩阵、任意精度模式、
限流熔断链路追踪、前端页面等一长串候选。

**问题**：题面没有给功能清单，意味着**「多做一个接口」不是加分而是负债** ——
每多一个接口就多一份语义要维护、多一处可能自相矛盾。spec §1 把这层判断写成了设计基调：
**砍到不能再砍**（spec `:23`）。

### 第 2 轮：v1→v2 砍接口族与存储子系统

评审推翻了三项设计、删除两个接口族（详见 spec §12 的决策记录 D1–D9）：

| 砍掉的 | 为什么站不住 |
|---|---|
| `POST /binary`、`POST /unary` 结构化算子接口 | 功能被 `/calculate` **完全覆盖**：`{operator:"add",left:1,right:2}` 与 `{expression:"1+2"}` 语义等价。唯一站得住的理由是「客户端不必拼字符串」，但能力清单暴露算子符号后该理由不成立（D1） |
| 内存寄存器 `M+` / `M-` / `MR` / `MC` | HTTP 客户端可自行持有状态，且变量可完全替代。唯一不可替代点是 `M+` 的原子读-改-写，单用户场景下无意义（D2） |
| `pow` / `mod` 函数形式 | 与 `^` / `%` 是同一能力的两种拼写，属设计噪音。由此得出**一般化规则**：函数集只收录无法用中缀表达的运算（D3） |
| 用户变量可覆盖内置常量（`pi = 3`） | 会让 `sin(pi)` 的含义随写入操作静默改变，破坏表达式可重现性。常量属于语言，不属于缺省值（D4） |
| 历史记录来源 `type` 字段 | D1 的连带结果：单入口下该字段恒为同一值，是死重（D5） |

### 第 3 轮：MVP 裁剪（本期实际交付）

设计定了，但**设计与交付范围是两件事**。本期按「尽快跑起来、可验收」的目标再裁一次，
裁掉的不是设计而是**实现范围**，逐条记在 [`docs/mvp-and-roadmap.md`](mvp-and-roadmap.md)：

- **只做求值闭环**：表达式原文 → 词法 → AST → 求值 → 响应。
- **变量与历史整体顺延**：它们各自是一块独立的第二能力域，不是「能算出一个数」的必要条件。
- **能力清单接口本来也打算顺延，后来拉回本期交付**（见第四节）。

这一轮的关键判断是：**先把「能算对」这件事做扎实**。数值核心（`Numbers` 与 `CalcNumber` 家族）
因此经过 4 轮加固，覆盖精确幂位数预算、scale 溢出、非有限值不变量、阶乘量级等**实测出来的**缺陷类 ——
它是本期最扎实的一环，不需要 Phase 2 返工（[`docs/mvp-and-roadmap.md`](mvp-and-roadmap.md) §二.5）。

## 三、功能边界

### 3.1 做：本期交付 3 个端点

| # | 方法 | 路径 | 职责 | 设计出处 |
|---|---|---|---|---|
| 1 | `POST` | `/api/v1/calculator/calculate` | 表达式求值，返回结果与结果所在数值路径 | spec §7.1（`:351-375`） |
| 2 | `GET` | `/health` | 健康检查：状态与已运行时长。**不带 `/api/v1` 前缀** | spec §7.5（`:488-490`） |
| 3 | `GET` | `/api/v1/calculator/functions` | 服务能力清单：接口、函数说明与能力边界 | spec §7.2（`:377-430`） |

第 2 条路径不带前缀是有意的：spec 的总则写的是「统一前缀 `/api/v1`」（`:349`），
而健康检查在端点表（`:50`）与 §7.5（`:488`）两处都**明文写作 `/health`** —— 具体条目的明文优于总则。

围绕这 3 个端点，本期实际实现的能力：

| 能力块 | 内容 |
|---|---|
| 词法与语法 | 表达式原文值对象、词法分析、AST 与优先级爬升式递归下降解析、算子优先级与结合性的唯一事实来源 |
| 求值 | 四则、幂、取余、阶乘、括号、一元正负号；23 个一元函数、5 个二元函数、2 个内置常量 |
| 数值模型 | 混合精度：`BigDecimal` 精确路径 + `double` 超越路径；浮点结果 15 位规整；非有限值拒收 |
| 角度语义 | 三角函数默认角度制（`sin(30) = 0.5`），请求级可切弧度制 |
| 错误处理 | 12 个错误码到 HTTP 状态的集中映射 + 统一错误响应体 |
| 配置 | `application.yaml` 四个 `calculator.*` 键，启动时校验并快速失败 |
| 交付形态 | 可 `java -jar` 运行的独立 jar；分层测试与端到端验收测试 |

### 3.2 不做 / 顺延，以及理由

**这一节是本次需求分析的重心：每一条都给出「不做的理由」，而不只是「不做」。**

| 不做 / 顺延的 | 理由 | 归属 |
|---|---|---|
| **变量存储**（`VariableName` / `Variable` / `VariableSet` 聚合根、变量用例、`/variables` 系列接口） | 变量是独立于「求值」的第二块能力域，有自己的一套不变量（命名规则、保留名冲突、覆盖语义）和一整套接口，但**不是「能算出一个数」的必要条件**。先让求值闭环跑通 | Phase 2（roadmap §二.1） |
| **计算历史**（`CalculationHistory` 聚合根、容量淘汰、分页、清空、`/history` 系列接口） | 历史是「求值」之后的**记录**能力，不影响单次计算是否正确；它引入容量策略、并发与分页这些与计算无关的复杂度 | Phase 2（roadmap §二.2） |
| **配置的运行时可变性**（在线改角度制 / 精度 / 上限的接口） | 配置在启动时读一次并校验；能改配置的接口会带来并发语义问题，属运维能力而非计算能力 | Phase 2（roadmap §二.4） |
| **更深的测试与评审深度**（逐任务深度评审、每条边界都有测试） | 本期以「可运行、主流程正确、关键边界有覆盖」为目标。**已投入的部分不缩水**：数值核心经过 4 轮加固 | Phase 2（roadmap §二.5） |
| **逐任务的深度评审** | 与上一条同因：评审深度随风险调整，见 roadmap §五「评审深度低于原计划」 | Phase 2 |
| 用户体系、鉴权、多租户 | 题面未要求；加了就需要用户体系，超出范围（spec §13） | 不做（YAGNI） |
| 持久化与落盘 | 题面明确「仅内存存储」；内存实现意味着重启即丢、不支持多实例横向扩展，这是约束的直接结果，非缺陷 | 不做 |
| 表达式化简、符号求导、方程求解 | 属「计算机代数系统」而非计算器；每一件都是独立的大工程，且无法用「一次 HTTP 求值」验收 | 不做 |
| 复数、矩阵、任意精度模式 | 会把数值模型从两条路径扩成一张矩阵，收益与成本不成比例（spec §5.1 的 `sealed` 两实现是刻意收窄的） | 不做 |
| 限流、熔断、链路追踪 | 单实例内存服务，无外部依赖，这些是分布式关切 | 不做 |
| 前端页面 | 题面要的是 HTTP 后端；只交付 JSON API，连静态资源映射都显式关掉（`spring.web.resources.add-mappings: false`） | 不做 |
| 结构化算子接口 `/binary` `/unary`、内存寄存器 `M±` | 见第二节第 2 轮：功能被覆盖或本就无意义（spec §12 D1 / D2） | 已否决 |

### 3.3 数值范围：写成契约，而不是「尽量支持」

用户明确要求先明确数值的计算范围，因此本期把它做成一份**显式契约**（spec §5.3）：

- **范围内的输入保证算得对**；范围之外一律**拒收**（抛领域异常 → 4xx），
  不保证给出哪个错误码，也不承诺优雅降级。
- 刻意**不追求**「对任意极端输入都给出有意义结果」：那种目标没有上界，而计算器的价值在于
  对**常用域**精确可靠（spec `:212`）。

具体数字表（scale 上界、精确幂位数预算、阶乘上界、有效数字、除法精度、表达式长度、
反双曲自变量上界、`round` 上界）与对应的代码出处，见 README 的「数值计算范围」一节 ——
那张表是**逐条回源码核对**后写的，每个数字都有 `文件:行号`。

### 3.4 接口契约上的两处不对称（有意为之，不是疏漏）

两个响应体的 null 形态**不同**，且这是设计选择：

| 响应 | 形态 | 机制 | 理由 |
|---|---|---|---|
| 成功响应 `CalculateResponse` | `angleUnit` 为 `null` 时**字段在场且值为 JSON null** | 该类**没有** `@JsonInclude` | 「字段在场且为 null」比「字段缺席」更能表达「本次求值不涉及角度」 |
| 错误响应 `ErrorResponse` | 为 `null` 的字段**整个不出现** | 该类**有类级** `@JsonInclude(NON_NULL)`（`interfaces/error/ErrorResponse.java:11`） | 避免调用方把 `position: null` 误读为 0 |

**这两处都不能说成「spec 的明文要求」**，spec 对它们的规定读法与实际情况如下：

- spec §7.1 的 200 样例（`:355-367`）**只给出 `angleUnit` 取值非 null 的一种形态**，
  对 null 形态**没有作任何规定**。「非三角表达式 → `angleUnit` 为 null」是领域对象
  `Calculation.angleUnit` 的语义，由 DTO 如实序列化出来。
- spec §7.6 对错误响应的规定是：「`position` 仅在与位置相关的错误中出现，其余为 `null`」（`:506`）。
  **主导句是「仅在与位置相关的错误中出现」**，省略字段正满足它；末句是取值语义的补充。
  所以错误响应省略 null 字段**不构成对 spec 的偏离**。
- 顺带说明一句容易引错的话：spec `:449` 那句「`angleUnit` 仅对三角函数相关的记录有意义，
  其余记录该字段为 `null`」出自 §7.3 **历史记录**一节，讲的是**历史条目**的字段，
  不是对求值响应 Null 形态的要求，不得引作依据。

两个契约各自有意，**不要试图「统一」** —— 统一必然要改已冻结的 `ErrorResponse`（那是悄悄改对外契约）。

### 4.3 本期**不覆盖**的用例（如实标注，不伪造覆盖）

| 用例 | 为什么不覆盖 |
|---|---|
| 变量定义后参与计算、变量覆盖语义、`PUT /variables/{name}` 保留名冲突被拒 | 本期没有变量存储 —— 这条不变量**部分**成立：请求级 `variables` 的保留名校验已做（E11），缺的是「跨请求参与计算」那一半 |
| 历史记录条数与分页、清空历史 | 本期没有计算历史 |
| 传 `Accept: application/xml` | 实测得 `406 + 空响应体`：兜底 handler 被调用了一次，但它产出的 JSON 在「客户端只接受 XML」的前提下渲染不出来。spec 未定义 406，**如实记为已知边界，不为它造断言** |
| `MethodArgumentTypeMismatchException` 分支（路径 / 查询参数类型不符） | 需要带类型化路径或查询参数的端点，本期 3 个端点都不绑定它们，因此**本期不可达**。分支刻意保留（见 [`docs/02-架构设计.md`](02-架构设计.md)） |

## 五、验收标准

### 5.1 spec §14 的八条（逐条判定）

| # | spec §14 条目（spec `:656-663`） | 判定 | 说明 |
|---|---|---|---|
| 1 | `mvn clean package` 成功，产出 `target/scientific-calculator-0.0.1-SNAPSHOT.jar` | **达成** | 构建命令由本人执行（见 README） |
| 2 | `java -jar …` 直接启动，无任何中间件依赖 | **达成** | 启动命令由本人执行；无数据源、无连接池、无外部调用 |
| 3 | `POST /api/v1/calculator/calculate` 传 `{"expression":"1 + 2 * sin(30) ^ 2"}` 返回 `result: 1.5` | **达成** | 用例 U1 |
