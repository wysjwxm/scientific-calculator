# MVP 交付范围与后续建设清单

本文档界定**本期交付（MVP）**的范围，以及**后续完整建设（Phase 2）**待补的功能。目的是让 MVP 尽快跑起来、可验收，同时不丢失原始设计中已经想清楚的部分 —— 砍掉的功能在这里有据可查，Phase 2 可以按图施工。

设计权威仍是 `docs/superpowers/specs/2026-09-12-scientific-calculator-design.md`（v3）。本文档记录的是**对该 spec 的有意裁剪**，不是对它的否定。

---

## 一、MVP 包含什么

**一句话**：提交一个表达式，拿回一个结果；独立 jar 直接跑，不依赖任何中间件。

| 能力 | 内容 |
|---|---|
| 词法 / 语法 | 表达式原文值对象与词法分析、AST 与递归下降解析器、算子优先级与结合性的唯一事实来源 |
| 求值 | 四则运算、幂、阶乘、取余、括号、一元正负号、常用一元/二元数学函数、数学常量（π、e） |
| 数值模型 | 混合精度：`BigDecimal` 走精确路径、`double` 走超越函数；结果规整；非有限值拒收 |
| 角度语义 | 三角函数默认角度制（`sin(30) = 0.5`），可切换到弧度制 |
| 精度策略 | 除法按可配置精度截断（默认 34 位），精确幂按结果位数预算限流 |
| HTTP 接口 | 求值接口 + 健康检查；统一的错误码到 HTTP 状态映射；统一错误响应体 |
| 配置 | `application.yaml` 四个键（角度制、除法精度、表达式长度上限、历史容量），启动时校验 |
| 交付形态 | `java -jar` 可运行的独立 jar；一个端到端验收测试 |
| 文档 | README、交付说明（含每步 AI 参与度标注）、本清单 |

**原始硬性约束全部保持**：Java 17 + Spring Boot 3 + Maven + JUnit 5；不引入任何第三方依赖；不用 MySQL/Redis/任何外部接口；全部内存实现；只做后端。

**数值范围是一份显式契约**：支持范围、范围之外「一律拒收、不做特殊处理」的处置方式，以及这样取舍的理由，写在 spec **§5.3 数值计算范围（契约）**。这一条刻意的选择是：**对常用域保证精确可靠，对极端输入明确拒绝** —— 不追求「任意极端输入都算出有意义结果」这种没有上界、也无法验收的目标。

## 二、MVP 不做什么（Phase 2 待补）

每一项都标注了「不做的理由」和「Phase 2 需要补什么」。

### 1. 变量管理
- **不做**：`VariableName` / `Variable` 值对象与实体、`VariableSet` 聚合根、变量用例、变量增删改查接口。
- **理由**：变量是独立于「求值」的第二块能力域，有自己的一套不变量（命名规则、保留名冲突、覆盖语义）和一整套接口，但它不是「能算出一个数」的必要条件。先让求值闭环跑通。
- **Phase 2 需要补**：值对象与聚合根（`ReservedNames` 已在 MVP 中实现，正是为它准备的）、`VariableUseCase`、变量控制器与相关 DTO、`/api/variables` 系列接口。
- **对 MVP 的影响**：表达式里出现标识符时，只认函数名与常量名，不认变量；查不到即报错（错误码 `UNKNOWN_VARIABLE` / `VARIABLE_NOT_FOUND` 已在错误码词汇表里预留，MVP 不会用到）。

### 2. 计算历史
- **不做**：`CalculationHistory` 聚合根、环形缓冲与容量淘汰、分页查询、清空历史、历史接口。
- **保留**：`Calculation` 结果记录本身 —— 它是**求值路径的产出**（`CalculationUseCase.calculate` 的返回类型、`CalculateResponse.from` 的入参），不是历史路径的一部分。但字段裁到三个：`(ExpressionText expression, CalcNumber result, AngleUnit angleUnit)`；原设计的 `id` / `elapsedMs` / `createdAt` 一并去掉，因为 MVP 里没有消费者，而 `id` 本应由历史聚合根分配 —— 在没有历史的情况下没有任何正确值可填。Phase 2 建聚合根时加回这三个字段。
- **理由**：历史是「求值」之后的记录能力，不影响单次计算是否正确。它引入容量策略、并发与分页这些与计算无关的复杂度。
- **Phase 2 需要补**：聚合根（内存 `ArrayDeque` + 读写锁 + FIFO 淘汰）、`HistoryUseCase`、分页响应 DTO、历史控制器。
- **对 MVP 的影响**：每次求值不落库、不留痕；spec §14 验收里依赖历史记录条数的那几条，顺延为 Phase 2 验收（见第四节）。

### 3. 能力清单接口（`GET /api/functions`）
- **不做**：算子表与函数注册表的对外清单接口。
- **理由**：它是对外暴露元信息，不影响计算能力；算子表与注册表本身在 MVP 中**已经实现**，Phase 2 只是加一个把它们序列化出去的控制器。
- **Phase 2 需要补**：`FunctionsResponse` 与对应控制器方法（含排序稳定性 —— 常量清单必须保序，不能用 `Set.copyOf`）。

### 4. 配置的运行时可变性
- **不做**：运行期修改角度制/精度/上限的接口，多套配置档位。
- **理由**：MVP 的配置在启动时读一次并校验；能改配置的接口会带来并发语义问题，属于运维能力而非计算能力。
- **Phase 2 需要补**：配置刷新接口与并发安全的重建策略。

### 5. 测试与评审深度
- **不做**：逐任务的深度评审（变异测试证明断言非空转）、每一条边界都有测试。
- **理由**：以可运行、主流程正确、关键边界有覆盖为目标。
- **已投入的部分不缩水**：数值核心（`Numbers` / `CalcNumber` 家族）已经过 4 轮加固，覆盖精确幂位数预算、scale 溢出、非有限值不变量、阶乘量级等实测出来的缺陷类 —— 这部分是 MVP 里最扎实的一环，不需要 Phase 2 返工。
- **Phase 2 需要补**：补充边界测试（尤其是变量与历史两块）、端到端覆盖扩展、一次完整的全分支评审。

## 四、验收范围

**MVP 验收**（可执行）：
1. `mvn test` 全绿。
2. `java -jar target/*.jar` 能在无中间件环境下启动。
3. 提交 `1 + 2*sin(30)^2` 返回 `1.5`。
4. 除零、语法错误、非法字符、非有限结果分别返回对应的错误码与 HTTP 状态，响应体为统一错误结构。
5. 表达式长度超限被拒。

**顺延到 Phase 2 的验收项**（原 spec §14 中依赖变量与历史的条目）：变量定义后参与计算、变量覆盖语义、保留名冲突被拒、历史记录条数与分页、清空历史、能力清单内容与顺序。

## 五、已知取舍与风险

| 取舍 | 影响 | 何时该重新评估 |
|---|---|---|
| 无变量 | 表达式只能算常量表达式，不能存中间结果 | Phase 2 第一优先，因为它影响接口形态 |
| 无历史 | 服务无状态、不可回溯 | Phase 2，与变量并列 |
| 错误码词汇表比 MVP 实际用到的多 | 有几个码（`UNKNOWN_VARIABLE`、`VARIABLE_NOT_FOUND`、`HISTORY_NOT_FOUND`）在 MVP 中不会被触发 | Phase 2 补上对应能力后自然消化；词汇表保持完整是刻意的，避免 Phase 2 改动接口契约 |
| 请求级变量保留，但**没有命名校验** | `POST /api/calculation` 仍接受请求体的 `variables` 映射（spec §7.1 的请求形态不变），但没有变量存储、也没有保留名校验 —— 请求里传 `{"pi": 3}` 这类与常量名冲突的键，会覆盖内建含义，而不是像完整设计那样被拒。**已在代码中核实**：`ExpressionEvaluator` 的查找顺序是先 `context.lookup(name)`、查不到才找内建常量，所以 `sin(pi)` 在传了 `{"pi": 3}` 时确实算成 `sin(3)` | Phase 2 补变量能力时一并收紧（`VariableName` + `ReservedNames` 校验，D13 的单一收口点）；在此之前这是「能用但不设防」的已知缺口。注：MVP 里没有变量存储，也就没有第二个入口，spec 担心的「同一表达式在不同入口下含义不一致」在本期并不存在 —— 遮蔽只可能由调用方在同一请求里显式传入造成 |
| 评审深度低于原计划 | 变量/历史两块的缺陷要到 Phase 2 才暴露 | Phase 2 动工前先补一次评审 |
| 内存实现无持久化 | 重启即丢 | 若需求变成「多实例/持久化」，需要重新做架构决策（当前明确不引入存储） |
